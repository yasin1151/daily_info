## 2. "AI 写代码快过我读代码"，那 Code Review 也交给 AI 吗

摘要：楼主在做开源游戏引擎 EVEngine，同时开 Codex、Cursor、DeepSeek 几个 Agent 并行，一天下来产出大量 PR，出现了尴尬的倒挂：写代码的速度已经超过自己读代码的速度。他现在的做法是让 Qodo AI Review 加 CI 约束先过一遍，Agent 再逐条回复并修复 AI 审出的 bug。但他自己抛出了那个绕不过去的问句——如果不放心 AI 写的代码，凭什么放心另一个 AI 审出来的结果？24 楼回复基本分三派：一派已经全面 Agent 化，人只定验收标准和方向；一派坚持人必须过目，只是把"逐行读"换成"读计划 + 读测试"；还有一派直接给数据，说交叉审能抓出绝大多数问题，只是钱包疼。为什么值得关注：今年团队工程流程的真瓶颈已经从"写"转到"验证"，这条帖是目前少见的、把"AI 审 AI"的成本和失效模式摊开讲的地方，评论里还有 Anthropic 官方 code review 访谈的链接作参照。

评论：
- 楼 19 broadliyn（信息量最大，直接引官方实践）：「刚好昨天 claude 官方就分享了他们的 code review 访谈。基本就是人负责定义验收标准，code 已经 review 不完了，那就索性不 review 了。出问题了怎么办？把精力放到如何快速恢复回滚上面。可能 ai 时代，的确要换种思维去面对传统软件工程。」
- 楼 3 midsolo（唯一给出制度化方案的公司实践）：「我司用的 openspec，搞了套'筛选 + 打分'的混合质检机制，AI 把需要质检的需求筛选出来并进行打分，分数低质量差的人工质检，剩下的全部 AI 质检。」
- 楼 15 yuanmomo9090（❤2，最真实的代价描述）：「先聊天，聊一个 plan，包含了所有的实现细节，甚至改动哪个文件……然后再让 AI 实现，即便这样，AI 依然会漏掉一些逻辑没实现。然后我人工一个个看，再用另一个 AI 交叉 review，一直到两个 AI 都 OK，真的是很浪费时间和精力。」同楼补了反例：同事纯 AI 写的大几千行 PR，他用几百行、更好的设计重写了。
- 楼 18 GeminiPro（最不政治正确但最像现实的一句）：「如果是为自己服务，当然不放心交给 AI，但现在整个世界都处于一种既不理性的狂热状态，老板都不在乎质量问题，那还说啥，直接蹬就完事了。」
