
## 1. 新手如何在复杂 UE 项目里安全接入 C++ 系统

**摘要：** 这条帖子的核心问题不是“能不能写 C++”，而是“在 Game Animation Sample 这类已经由 Blueprint、AnimBP、移动逻辑和动画系统共同驱动的复杂项目里，怎样先理清所有权边界，再把新能力接进去”。楼主已经能把飞行逻辑写出来，但一接入现有框架就和动画、移动、姿态保存等系统互相抢控制权。这个问题值得看，是因为它直接对应 UE5 里最常见也最容易踩坑的扩展方式：新代码不是越多越好，先弄清楚谁负责状态、谁负责表现、谁在驱动更新顺序，才能避免后面一连串系统互相打架。评论区也给出了一致方向：不要一上来就啃最复杂的样板工程，先补基础，再理解 Mover、Control Rig、CMC 和 GAS 之间的边界，必要时用更模块化的模板降低耦合。

**高赞评论：**
1. u/Ilithius（赞数：隐藏）：建议新手别直接跳进 Game Animation Sample / Lyra 这种高复杂度项目，先熟悉 UE 生态，再通过“新建类 + 接入现有项目”的方式理解边界。立场说明：这条评论的价值在于把问题从“怎么写功能”拉回到“怎么理解项目结构”。
2. u/CognacThrowback（赞数：隐藏）：指出 GASP、Motion Matching、Mover 都依赖更底层的基础知识，先理解 Control Rig 和 Mover 的工作方式，再去做飞行、游泳等状态扩展会更稳。立场说明：这更像是一条架构建议，重点是先学清楚系统之间的关系，再做定制。
3. u/tcpukl（赞数：隐藏）：直接追问楼主到底要在动画系统里实现哪些能力，说明这个问题必须先收窄到具体目标，才好判断该改 C++、Blueprint 还是两边一起接。立场说明：这条评论提醒读者，复杂 UE 项目的扩展不能空谈“加功能”，必须先定义功能边界。
