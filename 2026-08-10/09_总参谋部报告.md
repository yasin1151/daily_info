### 1. Codex 一开 full access，文件真能删穿磁盘
- **来源**：V2EX
- **一句话人话版**：有人在 Windows + WSL 环境里让 Codex 执行清理命令，结果因为引号、路径和删除命令组合失控，误删了大量文件。
- **新闻/帖子本身**：这帖不是单纯“模型写错命令”，而是 agent、沙盒边界、命令拼接和高危删除操作一起翻车。楼主把自动化权限给得太满，又让工具直接跑清理动作，最终把原本想处理的目录边界变成了全盘风险。它最刺耳的地方在于：这类事故不是假设题，而是重度自动化用户真的会碰到的实战事故。
- **社区原话摘录**：
  - V2EX 4 楼（1 赞）：“Windows 命令行老坑了。虽然 Linux 和 Mac 上也有这种问题，但 Windows 出这种问题的概率更高，很多误删都源自引号和转义。” —— 这条把锅先放在命令行生态和转义细节上。
  - V2EX 5 楼：“问题核心在于 WSL 挂载盘符、`find -delete` 高危命令、非隔离执行和非隔离删除，而不是单纯 PowerShell。” —— 这条更接近事故本体：危险的是执行边界，不是某个单一 shell。
  - V2EX 6 楼：“Bash 并不能天然避免这类事故，关键还是执行隔离和路径边界控制。” —— 这条很关键，意思是换 shell 不等于换安全。
- **参谋部短评**：这条值得继续盯，因它直接暴露 agent 自动执行的权限边界问题。真正的争议不是“会不会写命令”，而是“能不能安全地给它删文件权限”。
- **链接**：https://www.v2ex.com/t/1233011

### 2. 公益 Codex 中转站被注入，目标直指 ssh 和 API key
- **来源**：V2EX
- **一句话人话版**：有人在一个 codex 中转站里跑 full access，结果遇到提示注入脚本，目标是偷 ssh、apikey 和各种配置文件。
- **新闻/帖子本身**：这帖把代理型 AI 的安全问题讲得很直白：一旦工具能读宿主机文件系统，风险就不只是“prompt 被带偏”，而是凭据外泄和本地密钥被直接扫走。楼主看到的是一段明显针对 `.codex`、`.claude`、ssh、云账号配置的脚本注入，说明攻击者已经在把 AI 中转站当成现实攻击面，而不是玩笑。帖子真正让人不舒服的是：这里面有平台设计脆弱、权限过大、以及安全意识不足三层叠加。
- **社区原话摘录**：
  - V2EX 3 楼：“该站点此前就公告过脚本注入、窃取配置文件 API key 的问题，这次又出现说明风险并未解决。” —— 这条是在说，问题不是偶发，而是老毛病反复发作。
  - V2EX 4 楼：“中转站的多种攻击方式” —— 还附了相关仓库，意思是这种攻击面是可复现的一类，不是孤例。
  - V2EX 6 楼：“公益站实际仍靠付费用户支撑，侧面反映这类平台在安全和商业模式上都很脆弱。” —— 这条把安全问题和商业模式脆弱性连起来了。
- **参谋部短评**：这条舆情很值得盯，因为它不是模型幻觉，而是凭据级风险。只要 agent 还会碰本地密钥，这类事故就会持续出现。
- **链接**：https://www.v2ex.com/t/1233104

### 3. AI 生成一堆代码后，怎么 review 才不把项目写成新屎山
- **来源**：V2EX
- **一句话人话版**：楼主问的是实际工作问题：AI 在熟悉模块里很稳，但一碰陌生旧代码、长上下文和乱风格，质量就容易掉，怎么审才能兜住。
- **新闻/帖子本身**：这帖讨论的不是“AI 能不能写代码”，而是“写出来的东西怎么验”。评论区聚焦在测试覆盖、CI 全量跑、职责拆分和审查流程上，核心共识很清楚：AI 只是把决策节奏加快了，并没有替你消掉决策成本。真正麻烦的是，很多团队一旦进入陌生模块，就会把 AI 当速写工具用，最后把原本就乱的代码库再叠一层。
- **社区原话摘录**：
  - V2EX 2 楼：“除不可自动化部分外，应尽量做到全分支单测覆盖，CI 必跑全部测试。” —— 这是标准的质量兜底派。
  - V2EX 5 楼：“AI 只是降低决策间隔，没有降低决策成本，所以责任和决策流程仍要明确。” —— 这句很关键，点破了效率幻觉。
  - V2EX 6 楼：“建议拆成‘实施模型’和‘审查模型’，用不同模型互相拷打，避免单模型一路跑偏。” —— 这条是很典型的实操派建议。
- **参谋部短评**：这条值得继续看，原因是它已经从“能不能生成”转到“怎么控质量”。对真正在代码库里接 AI 的团队，这才是硬问题。
- **链接**：https://www.v2ex.com/t/1233025

### 5. 自我审查一旦没边界，就会无限循环
- **来源**：Reddit / r/ClaudeCode
- **一句话人话版**：大家在讨论 Claude Code 的 review 机制时发现，审查如果还是交给同一个模型同一个会话，很容易一直“再看看”，最后卡死在循环里。
- **新闻/帖子本身**：这个帖子的重点不是“要不要 review”，而是“review 该怎么停”。评论区其实已经给出很明确的方向：审查必须有独立上下文、独立阶段和明确停止条件，否则模型会把一点小问题无限放大，最后把一个本来能结束的任务拖成永不完工的打磨。这个争议对所有 agent 工具都很现实，因为只要流程没分开，模型就会倾向于继续找问题而不是收口。
- **社区原话摘录**：
  - Reddit 评论者（8 赞）：“The reason it loops forever ... has no bottom to it. There is always one more thing...” —— 这句把无限循环的根因说得很透。
  - Reddit 评论者（4 赞）：“Don't, especially Opus... you could tell it to audit itself and it'd be on a loop forever...” —— 这条是很直接的经验警告。
  - Reddit 评论者（1 赞）：“The mechanical fix is to stop relying on the model remembering. Wire a Stop hook...” —— 这条最偏操作层，强调把停止条件写进流程里。
- **参谋部短评**：这条很值得继续看，因为它触及 agent 工具里最容易被忽略的风险：没有边界的自查，最后会吞掉效率。流程设计比口头提醒重要得多。
- **链接**：https://www.reddit.com/r/ClaudeCode/comments/1vjoyc3/

## 今日舆情温度
- **最热争议**：今天最热的点不是“AI 能不能写代码”，而是“AI 一旦真的接管执行和审查，边界该怎么设”。一边是 Codex 误删文件、密钥外泄这种硬事故，一边是 Claude Code 自审无限循环、跨会话协作带来的体验争议。讨论已经从能力本身转向权限、隔离、停止条件和工作流设计。
- **最现实的吐槽**：最现实的吐槽集中在三个词：权限太大、稳定性不稳、审查太累。用户不是在抱怨模型不会写，而是在抱怨一旦把它放进真实工作流，文件、密钥、上下文和 review 全都会变成风险点，最后还是要人来兜底。
- **最值得继续观察**：接下来最该盯的是 agent 工具的安全设计是否真会收紧，包括文件删除、密钥访问、跨会话协作和 review 停止条件。今天这些帖子已经很清楚地说明：工具越像“能干活的代理”，越不能只看输出质量，得看它会不会越权、失控和把流程拖死。

## 可以跳过
- 只讲“AI 编程环境更好用”的产品自述，信息量偏宣传，若没有真实评论就不优先放大。
- 纯宏观地讨论“agent 时代来了”“工作流重构了”的帖子，今天的读者更需要具体事故、具体吐槽、具体审查经验。
- 只有媒体或 digest 摘要、没有评论原文支撑的内容，除非争议点特别硬，否则容易空。
