### 1. Claude Code 一次派出 117 个子代理，20 分钟烧掉 5 小时额度

- **来源**：Reddit r/ClaudeCode
- **一句话人话版**：Claude Code 上线了"优雅停止点"，但社区真正吵的是子代理批量派出把整份额度一次吃光。
- **新闻/帖子本身**：Claude Code 近期新增"优雅停止点"：任务中途撞上 5 小时会话限制时，不再粗暴截断，而是先找一个合适的停止点，从每周额度里划出一小份把当前工作收尾、留下可续跑的上下文（分档推送，高档订阅每次触及限制都能用）。这条更新本身好评居多，却把真正的痛点挤到台面上：主会话不设模型档位与数量上限时，一次 fan-out 能派出 9 个甚至 117 个子代理，20 分钟内吃光一个 5 小时窗口，任务却几乎一个都没做完。讨论给出的防护办法成本很低：在项目规则文件里写一条子代理路由规则、设并发上限，或者用 hook 直接拦截。
- **社区原话摘录**：
  - Reddit 评论者：只说了一句 "Please review today's code following the standards md as usual." 就去开会，回来看到 "Your usage resets in 4 hours"，117 个子代理还在等他。 —— 说明失控不是罕见事故，一句日常的"按惯例审一下今天的代码"就能触发，额度在人离开屏幕时被吞掉。
  - Reddit 评论者："Sub agents always get spawned at the effort level of the main chat unless you set up a custom agent" —— 他因此固定只留两个档位（一个高档推理、一个高性价比档），并在规则里写明"除非我明确要求，否则只用这两个"。 —— 把模型档位和数量写进规则，是目前最实用的一层防护。
  - Reddit 评论者："Blew 5 hour limits in under 20 min after spawning 9 SAs and none finished what they were supposed to do so all those tokens were wasted!" —— 他事后固定要求同时最多 2 个子代理。 —— 用硬性并发上限替代事后祈祷，是社区反复给出的兜底做法。
- **参谋部短评**：官方在做"更聪明的限制"，但额度真正的黑洞是用户自己配置里的并发。跑多代理工作流的人，这轮讨论里的规则写法可以直接照抄。
- **链接**：https://www.reddit.com/r/ClaudeCode/comments/1wqagzu/

### 2. 58 分钟云会话账单 34.38 美元：订阅制到底被补贴了多少

- **来源**：Reddit r/ClaudeCode
- **一句话人话版**：一位 20 美元/月的订阅用户跑了一次 58 分钟的云会话，账单显示 34.38 美元，评论区开始算订阅被补贴了多少。
- **新闻/帖子本身**：帖子晒出一张云会话账单：58 分钟 34.38 美元，缓存命中 99%，缓存读取 1.098 亿 token，96% 的用量发生在 15 万 token 以上的长上下文区间。帖主的疑问是这笔 Cost 按什么口径计算——同一件事放在订阅制下本地跑，大约只占一个 5 小时窗口的四到六成。评论给出的解释很直接：促销赠送的额度按 API 定价扣费，所以烧得飞快，这才是大家留在订阅制里的原因。讨论最有价值的部分是几个按 API 价折算订阅价值的数字，对判断"用订阅还是用 API"是很硬的参照。
- **社区原话摘录**：
  - Reddit 评论者："The $100 credit ant gave us is payed at api rates, so yes it vanishes very quick" —— 并估算同样用量换成 API 计价大约要 400 美元，这才是订阅用户的真实体感来源。 —— 把云额度与订阅的计价口径说清楚了。
  - Reddit 评论者："It's not $400, it's slightly over $1000 per month on the $20 plan. $5000 on the max 5x and $9000 on the $200" —— 直接在数字上更正，给出按 API 价折算的订阅价值量级。 —— 判断该用订阅还是该用 API 时最实用的一条。
  - Reddit 评论者："$34 for a 58 minute task is pretty wild" —— 他把原因归到 1.09 亿次缓存读取上，认为 token 计数在 agent 反复读取巨大上下文之后早已失去直觉，计价展示方式需要重做。 —— 点出长上下文缓存读取是 agent 时代账单的主要驱动项。
- **参谋部短评**：这类帖子比任何定价页都更能说明订阅制被补贴了多少。争议点不在贵不贵，而在按量计费是否还让人算得清账，值得继续盯官方是否调整计价口径。
- **链接**：https://www.reddit.com/r/ClaudeCode/comments/1wqjjcf/

### 3. Apple Pay 万事达被盗刷：设备卡号被当普通卡号放行

- **来源**：V2EX（程序员节点，44 条回复）
- **一句话人话版**：中行万事达 Apple Pay 被盗刷，社区把技术根因定位到 Apple Pay 的虚拟设备卡号被当成普通卡号放行。
- **新闻/帖子本身**：帖主本人的中国银行万事达 Apple Pay 被盗刷，24 小时内同类案例集中出现（以中行万事达为主，少量招行、农行）。讨论的技术焦点是：Apple Pay 的虚拟设备卡号（Token 卡号）疑似被当成普通卡号，允许用"卡号 + 有效期 + CVV"三要素走无卡支付，等于绕过了 Apple Pay 的安全机制。对技术人来说，这是一次典型的"新渠道接入旧系统时走捷径"导致的安全回归——不需要任何数据泄漏就可能被枚举盗刷。回复里还给了一条立即可用的处置动作：在银行 App 里把境外交易限额设为 0。
- **社区原话摘录**：
  - V2EX 18 楼："该部分设备卡允许通过三要素进行支付，卡号采用顺序发卡，且不校验 CVV，同时可能并无 3DS 等额外校验措施，因此仅需通过稍加猜测或复用其他类似卡有效期即可实现盗刷" —— 目前社区里最接近根因的技术判断，且不需要任何数据泄漏。
  - V2EX 30 楼："这个漏洞根本不需要 token，甚至不需要经过 Apple……正常银行是不会允许这些三要素进行联机或者互联网交易的……如果他们的卡号顺序发行，那过期日期都是规律的，完全可以被枚举出来" —— 把责任指向发卡行没有校验交易来路，而不是 Apple 或万事达被攻破。
  - V2EX 39 楼："把 Token 卡号当作普通 PAN 卡号放行，且未触发风控拦截大批量异常的境外拉美交易，这是严重的后端逻辑漏洞" —— 另一派把账算在授权系统与风控缺失上。
- **参谋部短评**：与 AI 无关，但今天技术含量最高的一条。三方对"谁的责任"仍有分歧：Token 化设计、受理规则、发卡行授权校验。持卡人先锁卡、把境外限额压到 0 更实际。
- **链接**：https://www.v2ex.com/t/1244872

## 今日舆情温度

- **最热争议**：AI 到底在放大人的产出，还是在把人降级成机器里的齿轮。两条讨论合起来接近 650 条评论：一边是数学家写"我们需要更多的数学家"，主张人类有责任建立一支能读懂 AI 产出的知识储备，他给的理由很硬——如果 AI 提出一个太瓦级核聚变堆的设计，人必须能判断失效如何被控制，才可能批准建造；另一边是函数式程序员的自我辩护，说把想法表达出来这件事本身就是乐趣，生成代码会侵蚀这种乐趣。反方最直接的一句是"一旦 AI 数学远超人类，人的参与就像蚂蚁试图理解量子物理"；而被反复认同的观察来自生理层面：长时间读大段生成代码，代价比想象中高。还有人补了一句扎心的自省——"以前我逐行审查生成的代码几乎每次都能挑出问题，现在我挑出的越来越少了，也许是模型变强，也许是我在交付压力下变得没那么仔细了"。
- **最现实的吐槽**：额度和账单是今天最集中的槽点。有人一次派出 117 个子代理、20 分钟吃光 5 小时窗口，任务一个没完成；有人跑了 58 分钟云会话收到 34.38 美元账单，评论区顺手算出 20 美元档订阅按 API 价折算价值过千美元每月；有人领了赠送额度后升级订阅卡在身份验证，并吐槽云版本没有本地 MCP 和记忆，对重度用户价值有限；本地部署那边也有新账要算——27B 级模型在 12GB 显存上已经能用，但高推理档会把 128K 上下文在"思考"阶段烧光，显存之外还要额外吃掉约 12GB 系统内存。
- **最值得继续观察**：三件事。一是算力服务大面积中断之后的额度补偿，以及围绕 agent 在训练与评估期间联网的审查——官方称要在透明度和"从 PB 级活动日志里搞清楚发生了什么"之间平衡，进度比预期慢；二是巨头把对话助手升级成"Agent 工作台"（主页、编码、自动运行三合一），本月底进入私人预览，直接冲击各类自动化与文档 SaaS；三是 agent 训练的基础设施路线，已有厂商公开了每天服务约 300 万个沙箱、支持 38 万并发的生产级沙箱架构，训练瓶颈正从模型转向环境。

## 可以跳过

- 代码托管榜单前排的两个新项目：只有一句话定位和单日新增 star（一个主打"管一队 AI 员工"，一个主打"会学习的 agent 记忆"），没有使用反馈、没有基准复核，等一个版本再看更稳。
- 几条行业人物发言："采购标准从对人好用变成对 agent 好用"、"evals 是企业 AI 扩散的闸门"这类判断很锋利，但都是演讲式观点，缺少社区回应和反例，隔一天看是否有人反驳更有价值。
- 大额算力采购与"机器人访问政府网站"类报道：数字和措辞都很大，评论区主要在质疑报道口径本身，缺一手讨论，不适合放进舆情主榜。
- 榜单上重新露脸的老牌框架与高校课程类项目：只有存量热度或课程推介，当天没有新的争议和使用反馈。
