## 2. 关于对用户数据的责任：NeoVim 导致 Vim 的 undo 文件被删除

**HN 338 分 / 301 评论 | 原文：** https://unsung.aresluna.org/they-had-no-concept-of-a-duty-of-care-to-their-users/
**HN 讨论：** https://news.ycombinator.com/item?id=49867067

**摘要：** 作者 Marcin Wichary（前 Google/Medium/Figma 设计师，"Unsung"博客）引用了计算机科学家 David Chisnall 的一段经历：他从 2000 年开始用 vim 写了五本书、一篇博士论文和 150 多篇文章，持久化 undo 是他最爱的功能，能在重启、崩溃甚至隔几个月后还原编辑历史。而试用早期 Neovim 后，他打开文件发现 undo 失效——用 vim 打开也一样。Neovim 改了 undo 文件格式，既没升级旧格式，也没换文件名，直接覆盖了。作者借此批评软件行业"对用户数据缺乏注意义务"，违反 Raskin 第一定律：程序不得伤害用户数据，也不得因不作为让数据受损。

**值得关注：** 讨论分化成两半：一半是格式兼容的技术事实辩论，另一半是围绕维护者与社区 mob 的争议（原文里还牵出一段关于贡献者背书被撤下的风波）。这类"fork 吞掉上游用户数据"的案例，对任何做文件格式/本地缓存的团队都是提醒：破坏性格式变更需要版本化 + 重命名 + 明确报错三件套。

**热评原话：**
- `tmp_throwaway_q`（反驳文章）：*"undo 文件格式本来就带版本号，不是 YOLO 写的；Neovim 一直会报版本不兼容的错误。这里的义愤在我看来很莫名其妙……顺手来 GitHub 喷几句、对项目毫无其他参与的人是世上最难相处的一批人。"*
- `natbennett`：*"我很早就用 Neovim 了，我印象里它当时的定位就是'Vim，但带破坏性变更'。"*
- `manvillej`：*"说到底，说一句'白人至上主义是错的、我不认同'并不难，我只花了 10 秒。"*

## 6. 别把你的 Go 代码耦合到 GitHub

**HN 109 分 / 51 评论 | 原文：** https://iain.rocks/blog/dont-couple-your-go-code-to-github
**HN 讨论：** https://news.ycombinator.com/item?id=49868404

**摘要：** Go 的一个好设计是 import 路径即代码地址（`import "github.com/user/repo"`，go 自己用 git 拉取），省掉了中心化包管理，也让人一眼知道去哪报 bug。作者 Iain Cambridge 指出代价是代码与托管商强耦合：迁到 GitLab 就得改所有 import，否则还是在拉旧地址；于是"迁不动"本身成了技术债。他见过一家公司被迫同时维护 GitHub、GitLab、Azure DevOps 三套托管，就为了绕开迁移成本，直接烧钱。解决方案是自建命名域（`go.iain.rocks`、`go.uber.org`、`go.mongodb.org`）指向真实仓库，迁移时只改域名指向；文中附了完整的 nginx 配置。他的结论是：用 Go 的商业团队都该给内部库建自定义域名。

**值得关注：** 供应链与基础设施可移植性的老问题，在 Go 生态是默认踩坑位。评论区的反驳也很实在——自定义域名的存续寿命未必比 GitHub 长。

**热评原话：**
- `SenHeng`：*"GitHub 几乎是永恒的。你的自定义域名一停付账单就没了，而对开源开发者来说，这事发生的概率比 GitHub 消失高得多。总有一天我们都会回到 vendoring 依赖。"*
- `prasadvara`：*"这不就引入了域名管理这个新依赖吗？好处我理解，但等于给每个开源开发者加一层基础设施管理工作。"*
- `otterley`：*"我们一开始为什么要放弃 vendoring？"* → `metaltyphoon`：*"因为不方便。"*

**HN 36 分 / 5 评论 | 原文：** https://github.com/deepfates/imp
**HN 讨论：** https://news.ycombinator.com/item?id=49869995

**摘要：** 把 Stanford 的 DSPy（"编程而非提示词"的 LM 程序框架）完整移植到 BEAM（Elixir/Erlang 虚拟机）。你声明每一步的输入输出类型、选择推理方式，再由优化器用"好的样例"去迭代改进；提供 signature、module、optimizer、agent loop 和 retrieval。核心卖点是与 OTP 的结合：在 BEAM 上 agent 就是一个进程——自己持有状态、收发消息、被 supervisor 监管，和应用的其余部分一起跑。作者强调你永远不写 prompt 也不写 parser，Imp 从 signature 生成提示词、校验回复，给你类型化字段（枚举不合法就返回错误）。
