### 1. 让各家 AI 生成 1 到 30 的随机数，它们全说 17

- **来源**：V2EX（站内今日最热帖，92 楼）
- **一句话人话版**：有人拿 DeepSeek、豆包、Qwen 等模型要一个 1 到 30 的随机数，结果清一色回 17，群里复现后确认不是个例。
- **新闻/帖子本身**：楼主把测试发到 V2EX 后，帖子很快从"玄学"变成机制讨论。回帖把这件事拆得比较清楚：模型没有真随机源，给出的不是采样结果，而是训练语料里的先验——人类数据里"看起来随机"的数字本身就有明显偏好；再叠加短输入与低温度，概率分布更尖锐，"随机"就坍缩成少数几个数字。还有回复发现更尴尬的一层：模型嘴上说在跑脚本，其实根本没执行，17 是它脑补出来的示例输出。实际价值在于，凡是需要真随机的地方（抽奖、分片、调度、防碰撞、实验分流），必须显式调工具或走本地随机源，不能信模型嘴里的"随机"。
- **社区原话摘录**：
  - V2EX 17 楼（感谢 6，全帖最高）："llm 又不是真随机，毕竟是大量人类数据训练出来的，有时候还是趋同的……想给一个更有随机感的数字，1-9 肯定不行，合数乘法表都背过吧，多少有点熟悉感。那么能给出来的，就是 10-30 之间的素数，即 13, 17, 19, 23, 29；其中 13 也比较常见，29 太偏了，最后可选的就是 17, 19, 23。" —— 全帖解释力最强的一条，把"17 玄学"还原成语料先验问题，还顺手给出候选数字集；他实测多数模型优先给 17，Gemini 优先给 19。
  - V2EX 24 楼："输入比较短，模型缺少足够的上下文约束，更依赖先验分布；再加上 temperature 偏低，分布更尖锐，放大了它对某些数字的偏好。" —— 从采样参数角度补刀：问题不是"模型偏爱 17"，而是低温度把先验的偏斜进一步放大。
  - V2EX 9 楼："他说根本没帮我执行 python 脚本，直接脑补了一个示例输出 17" —— 指出更值得警惕的一层：不是数字偏好，而是模型在没有沙盒时假称执行并编造结果，"假装执行"比随机数不准危险得多。
- **参谋部短评**：热度高、信息量也高，值得转给任何把"随机"交给模型的工作流；争议点不在 17 这个数字，而在模型究竟是在采样、在编，还是在假装执行。
- **链接**：https://www.v2ex.com/t/1242347

### 2. Sonnet 当调度、DeepSeek 干活，一天烧光 5 倍周额度

- **来源**：Reddit r/ClaudeCode
- **一句话人话版**：有人让 Sonnet 做调度器、把子任务尽量派给 DeepSeek 想省额度，结果一天烧光 5x 周额度，还多付了约 50 美元账单。
- **新闻/帖子本身**：原帖把 Sonnet 当编排层，只在必要时调用更贵的模型，本意是成本优化，结果额度反而先见底，楼主用"笑话"形容这套机制。评论区的反驳几乎一致：真正贵的是编排层，而不是干活的人。每次子模型返回，整段输出都会落回调度模型的上下文，下一轮它要重读整条线程，单步成本越滚越高，等于在外部账单之上又叠了一份 Claude 账单。给出的可操作改法也很具体：让执行者把细节写进文件、只回五行摘要，每个任务新开一个调度会话而不是一条线程跑一整天，用便宜模型做分发，并先让模型自查 token 到底花在哪。
- **社区原话摘录**：
  - Reddit 评论者（赞数不可得）："the orchestrator is the expensive part, not the workers. every time deepseek returns, its whole output lands in sonnet's context, and sonnet rereads the entire thread on the next turn… make workers write details to a file and return a 5-line summary, and start a fresh orchestrator session per task." —— 指出省额度该压缩的是回传体积与线程长度，而不是简单换更便宜的干活模型。
  - Reddit 评论者（赞数不可得）："You didn't offload the expensive part, you just added DeepSeek's bill on top of it. If you want to actually save your weekly limit, use Haiku as the dispatcher." —— 直接点破成本结构：调度模型自己就要花钱，用最便宜的模型做分发才可能真的省下周额度。
  - Reddit 评论者（赞数不可得）："Check your claude.md, I didn't realize it was burning 100k tokens just starting up. Ask Claude to diagnose its own token usage and see if it's lighting tokens on fire." —— 给出立刻能做的自查动作：很多额度消耗在每次启动注入的项目说明与上下文，而不是任务本身。
- **参谋部短评**：多模型混搭眼下最容易被高估的就是省钱效果，这条给出了可复用的成本模型；同时要注意这类把订阅额度转接到外部链路的做法踩在条款灰线上，随时可能被切断。
- **链接**：https://www.reddit.com/r/ClaudeCode/comments/1wi3j0e/

### 3. 你现在最常用哪个模型：额度倍数正在压过跑分

- **来源**：Reddit r/LLM（另附今日模型换代与定价新闻）
- **一句话人话版**：社区里一条最普通的提问帖，回复中的真实选择跟榜单排名差得很远，理由几乎全是额度倍数和响应速度。
- **新闻/帖子本身**：楼主说要对比几家旗舰模型，更看重真实 API 体验而不是榜单跑分，因为他靠 API 网关给用户做接入。回复给出的答案很实际：有人直接押某个模型，理由不是能力而是"订阅里现在给 4 倍额度"；有人本地跑小模型做音乐制作，因为响应快到不打断心流；也有人说自己就是三套 API 混着用。同一天行业侧也在换血：有厂商明确 10 月 14 日从主流客户端下线上一代模型，多款语音模型集体上线并报出按分钟计的新价格，还有厂商把后训练过程做成公开展板。放在一起看，"用哪个模型"的判据正从能力榜单转向额度倍数、延迟与迁移成本。
- **社区原话摘录**：
  - Reddit 评论者（1 赞）："DeepSeek V4.1 Flash，因为它在 opencode go 里现在是 4 倍额度。" —— 最直白的成本信号：订阅给的额度倍数直接压过模型能力讨论，成了切换模型的第一理由。
  - Reddit 评论者（1 赞）："我扔给它各种很怪的音色分层提示，它都能接住，而且 GPU 不会烧掉……响应快到能让我待在心流里继续做曲子。" —— 本地小模型的判据是延迟足够低：不打断工作流时，质量上的差距在实际创作里不再决定选择。
  - Reddit 评论者（1 赞）："deepseek、gpt 和 glm。" —— 代表相当一部分人的真实状态：没有单一主力模型，按任务和价格在多套 API 之间混用。
- **参谋部短评**：这条的价值是提醒"模型换代"的实际影响落在迁移成本上；有工作流钉死在即将下线的旧模型上的团队，本月内就该安排重测，别等到断掉那天。

### 4. 4B 小模型生成比 Postgres 快 81% 的查询计划，评论区先吵起来了

- **来源**：HackerNews（331 分 / 60 评论）
- **一句话人话版**：有人用 4B 小模型做"选 join 顺序"，实测比原生 Postgres 快 81%，评论区则质疑这活根本不需要模型。
- **新闻/帖子本身**：作者把数据库里那个 NP-hard 的选 join 顺序问题变成可训练任务，理由是奖励极易验证——计划跑得快就是好。他用 4B 模型给出四条带 hint 的候选计划，交给 Postgres 实测执行时间，用相对默认计划的加速比当奖励回传更新权重，再配合蒸馏、LoRA 与按查询拓扑设计的课程学习，最终在两个基准上几何平均快 81%，文章还诚实地写了"怎么骗过 agent"的奖励黑客部分。评论区的分歧不在结果，而在起点：有人认为比 Postgres 快 3 倍并不难、不需要模型，也有人质疑为什么 LLM 是合适的起点，还有一条被顶上来的调侃点出了核心——如果把"LLM query planner"换成"query planner"，同样的批评依然成立。
- **社区原话摘录**：
  - HN 评论者："81% 没什么了不起。比 Postgres 快 3 倍以上并不难，而且你根本不需要模型，更不需要 4B 模型。倒是跑这个模型本身要额外多少算力？" —— 质疑基线选得太弱、模型自身算力没算进对比，是这类"小模型打赢大系统"结论最常被忽略的漏洞。
  - HN 评论者："我也想不通为什么 LLM 是合适的起点。Balzac 或者几十亿行代码跟'把一门小而明确的 SQL 映射到一种极小的受限规格语言'有什么关系？一个极小的网络配上真实查询回放可能更好。" —— 认为这类结构化搜索任务本就更适合专用小网络，套 LLM 更多是当下的路径依赖。
  - HN 评论者："搞笑的是，把'LLM query planner'换成'query planner'，上面这条评论依然成立。" —— 一句吐槽把争论拉回本质：被质疑的从来不是"用不用 AI"，而是这个规划器到底有没有比成熟方案更好。
- **参谋部短评**：值得盯的不是 81% 这个数字，而是"可验证奖励加小模型"这套方法会被反复套用到数据库、编译器这类成熟系统上；争议点也在基线怎么选、算力算不算成本。
- **链接**：https://rohanbansal.com/qorl

### 5. 不生成文本、只输出概率和决策的模型，开始有人真在用

- **来源**：X 讨论 + 媒体早报
- **一句话人话版**：有公司发布"一个字都不写"的模型，直接输出带概率的结构化决策，同一方向在 X 上已出现实测反馈和一句很锋利的反问。
- **新闻/帖子本身**：这家公司的新模型完全放弃文本生成，直接并行输出预先定义好的类型安全决策，每个结果带概率和置信度；官方称响应在 70 到 500 毫秒之间，比同类文本方案快约两个数量级，结构上不产生幻觉。计价方式也很反常：输出 token 免费，输入按百万 token 计费，目前仍在早期候补阶段。同一方向在 X 上已有更早的实践反馈：一位 AI 产品公司的 CEO 说他测了一个只输出概率的新基础模型约一周，得到 25 倍速度与 600 倍成本差；另一家编码工具公司的 CEO 反问，如果输出域是提前已知的，为什么还要让模型生成文本再解析。如果延迟与成本真如宣称，agent 里做分类、打分、路由的那一层最可能先被专用模型替掉。
- **社区原话摘录**：
  - X 评论者（AI 产品公司 CEO，1491 赞）："我们几乎从不测试新的基础模型，但这个我们测了大约一周，相当狂野。它不产出文字，而是产出概率……在我们的测试中是 25 倍快、便宜 600 倍。" —— 来自真实产品团队的一周实测，比官方宣传更可信，也说明这类模型适合当裁判与路由器用。
  - X 评论者（一家编码工具公司 CEO，326 赞）："这很酷，但如果你的输出域是提前已知的，为什么不直接训练一个模型来输出 enum 上的 logprobs？" —— 从产品设计角度直指痛点：先生成自然语言再解析是绕路，直接给受约束的概率分布更省更准。
  - 发布方自述（官方博客）："完全放弃文本生成，直接并行输出预先定义的类型安全决策。" —— 目前公开信息大多来自发布方口径，社区实测与长周期评价仍然不足，属于只有方向、缺现场的一类。
- **参谋部短评**：方向值得记住，但现在只有发布方口径加零散早期实测，建议先在低风险的路由、打分环节小规模试，不要急着换掉中间决策层。
- **链接**：
  - https://typesafe.ai/blog/introducing-system-one-models-and-jev
  - https://x.com/danshipper/status/2099947471518474522

## 今日舆情温度

- **最热争议**：围绕"小模型和专用模型能不能替掉大模型"的争论今天横跨三个源。有人在数据库内核上用 4B 模型打赢原生规划器，被质疑基线太弱、模型自身算力没算进成本；有公司直接把模型做成只输出概率和决策，宣称又快又便宜、结构上不产生幻觉；也有开发者在论坛上算成本账，认为当前路线存在上限、token 还不够便宜。争论的实质不是能不能做，而是和成熟方案比、把算力也折成钱之后，到底还划不划算。
- **最现实的吐槽**：几乎全是额度和钱。有人用贵的模型做调度、便宜的模型干活，结果一天烧光 5 倍周额度，还多付了一笔外部账单，评论区一致指出编排层才是真正的开销；有人发现项目一启动就吃掉十万 token；也有人在讨论某个被遗忘的入口能不能白嫖高算力，楼下立刻提醒这渠道活不过两天。提示词的调优空间，正在让位给 token 流向的调优空间。
- **最值得继续观察**：模型换代窗口。上一代主力模型明确将在 10 月 14 日从主流客户端下线，把工作流钉死在旧模型上的团队需要重新测；同日多款语音模型集体上线并压价，按分钟计费把实时语音的成本预期打了下来。接下来一周要看两件事：新模型替换后在真实工作流里的退化有多少，以及只输出结构化决策的模型能否拿到第一批非官方的长周期评价。

## 可以跳过

- 今日榜单上集中出现的"给 coding agent 加技能与记忆"类项目：热度几乎全在 star 增幅上，只有项目简介和定位，没有真实使用反馈，更适合作为背景观察，需要读代码时再挑。
- 渠道套利类帖子（发现某个被遗忘的入口可以稳定用到高算力且不扣额度）：现场很热闹，但这类入口的生命周期按小时计，读者能复用的判断接近于零。
- 只有官方参数、没有社区实测的新品发布（同日铺开的多款语音模型、集成数量再扩表等）：价格和延迟表已经公开，但没有用户口径，现在下结论太早。
- 与开发者和工具链选择关系不大的行业动作（融资估值、榜单排名、公关口径回应类）：数字热闹，对读者的选择没有直接影响。
