**2. Codex CLI 默认静默安装常驻自更新后台守护进程** · 404分 / 218评
https://github.com/openai/codex/issues/48195

摘要：从 Codex CLI 0.157.0 起，只要打开一次交互式会话，就会启动常驻后台守护进程 `codex app-server --managed-daemon`：脱离 TTY、所有窗口关闭后仍驻留（被 PID 1 收养，直到重启），把约 374MB 平台包复制到 `~/.codex/...` 运行，并挂一个自更新循环（启动 5 分钟后检查、之后每小时），更新时可能强杀进行中的任务。附带副作用：用它启动的第一个会话的代理环境变量会被守护进程永久钉死。

- icantevenhold：「它还塞满我的硬盘，全是旧版本。我查了一下总共占了大约 12GB，就一个 harness 而已？大家抱怨 Claude Code 做得烂，但 Codex 在每一项指标上都更糟。」
- whimblepop 给出关闭方法：在 `~/.codex/config.toml` 写 `[features] daemon_auto_start = false`（目前藏在 feature flag 后面，无正式文档）。
- dingaling911 反方：「这东西迭代很快，就该自动更新，这已经是标准做法了。浏览器就是这么干的，harness 没理由不这么干。」
- timdorr：「这跟 Claude Code 的运营模式一样。」（并贴出 `ps` 里一堆后台任务和多个旧版本）
- thebeardisred：「这时候就体现出发行版模式的价值了——有人帮你打包、测试、给出合理默认值，并阻止这类小动作。」

为什么值得关注：本地开发工具正在变成常驻服务，「自动更新 vs 可审计/可控/可卸载」的冲突第一次被摆到台面上。对在 CI、沙箱、内网代理环境里跑 codex 的人是直接风险。

**4. 用 C 写现代 Web 应用（BCHS + CGI）** · 344分 / 153评
https://prophitt.me/writing/a-modern-web-app-in-c

摘要：作者 Corey Prophitt 用 1994 年的技术栈（OpenBSD + C + httpd + SQLite，即 BCHS）上线了一个商业产品 marketyour.games：用户账号、内容创作者搜索仪表盘、Stripe 支付、Postmark 事务邮件、渐进增强、完全不依赖 JS。没有框架、没有模板引擎、没有独立数据库服务、没有容器；每个请求 fork 一个新进程，静态资源全部编译进二进制并从内存提供。发版=替换一个文件，无需重启、零停机；构建只需几秒。

- hughw：「我不同意第一句。199x 年我认识的做网页的人是把 perl 脚本丢进 cgi-bin，不是 C 程序。」
- Panzerschrek 质疑并发写：「每次请求都起新进程，那多并发请求时怎么办？SQLite 允许多进程同时写吗？」
- Scubabear68：「文章说『在 C 里写 HTML 和 CSS 不算太糟』——呃，C 里的任何字符串处理都够呛。」
- EGreg 指出本质：「每个请求一个进程，这正是 FastCGI 存在的理由」，并类比 PHP 的 Swoole/FrankenPHP、Laravel Octane 等常驻方案。
- paularmstrong 顺带吐槽成品页面：「那句『marketyour.games 的一切都很现代』——那页面上除了标题我什么都读不清。」

为什么值得关注：反潮流但真实的工程样本——极小依赖、进程模型、单文件部署在 2026 年依然能扛商业产品，几乎无供应链攻击面。对照当下框架与依赖膨胀，值得当作基线反思。

**5. AI 编码 Agent 产出更多代码，但不是更多软件** · 290分 / 247评
https://arstechnica.com/ai/2026/10/ai-coding-agents-generate-more-code-but-not-more-software/

摘要：Ars Technica 报道一项研究：AI 编程 agent 确实大幅提升代码产出量，但收益被人类评审环节「吸收」——瓶颈从写代码转移到 review 与集成。研究基于 2025 年的模型（Claude 3.5→Sonnet 4.5、GPT-4.1→GPT-5、Gemini 2.5），因此讨论焦点之一就是「这个结论今天是否已经过时」。

- blauditore 打比方：「就像赛车厂比发动机，当发动机强到一定程度，瓶颈就变成轮胎抓地力。有人发明了超级燃料，车却只快一点点，因为多出来的动力没改变下限。软件也一样——编码只是其中一小部分。」
- staminade：「这与我职业中遇到的一致。代码评审一直是明显瓶颈，有了 agentic coding 后更严重。资深工程师非常难放弃逐行 review，不管 agent 变多好。」
- sroerick 反问：「有谁真的指望代码评审能逐行抓 bug 吗？我一直把 review 当基本 sanity check、推行最佳实践和带新人的场合。要担心出问题，我会去谈测试覆盖。」
- CharlieDigital：「agent 会写出一座重复度极高的测试代码山，没有明确指令就不愿重构。非平凡的集成测试很容易出现测试代码是实际交付代码好几倍的 LoC。第二个问题：不同模型/agent/harness 倾向不同，而且它们倾向于回避自己陌生的部分。」
- KumaBear 反向补充：「有一点我强烈不同意——自用软件的产出绝对爆炸式增长了。我过去想都不敢想的项目，现在都能做。」
- jefftk 提醒时效：「按学术论文惯例，这是描述研究进行时的世界状态。写出来、发出来之后，媒体又当成当下事件报道。这里看到的其实是 2025 年的画面。」

为什么值得关注：今年最值得记住的「AI 生产力天花板」证据链：产出量 ≠ 交付量，瓶颈的定价在组织流程而非模型能力。
