### 1. Claude Code 用户开始认真算 token 账：Hook 比 prompt 更像生产力工具
- **来源**：Reddit / r/ClaudeCode
- **一句话人话版**：Claude Code 用户复盘后发现，重复流程别再靠模型临场发挥，应该用 Hook 固化成脚本。
- **新闻/帖子本身**：一位长期使用 Claude Code 的开发者说，自己过去太关注 prompt 和 skills，却低估了 Hook。Hook 可以在 AI 工作流阶段插入确定性脚本，比如 lint、准备数据、工具调用前后处理。争议点不在功能新不新，而在 AI 开发进入重度使用后，token 比 CPU 贵，反复让模型“想一遍、写一遍”已经不划算。
- **社区原话摘录**：
  - Reddit 评论者（12 赞）：“让 Claude Code 写了插件，退出 plan mode 后把方案保存进代码仓库做版本控制；同一 session 继续对话会覆盖旧方案，所以插件会检测并新建文件。” —— 这条很工程化：把 AI 的计划变成类似 ADR 的可追溯资产。
  - Reddit 评论者（10 赞）：“类似 dynamic workflow，但设计为持久化并保存，让 agent 更容易写出自己的流程。” —— 关注点不是单次省 token，而是让 agent 流程变成长期可维护抽象。
  - Reddit 评论者（3 赞）：“做了自动创建并追踪任务文件的工具，提交到仓库当作 ADR；所有 agent 跑在沙箱里，agent 无关。” —— 这条把 Hook 思路扩展到跨 Codex、Claude 的通用工作流。
- **参谋部短评**：这条值得继续盯。社区正在从“怎么提示模型”转向“哪些步骤不要交给模型”，Hook、脚本、ADR 化记录会成为重度 agent 用户的基础设施。
- **链接**：https://www.reddit.com/r/ClaudeCode/comments/1vizi2d/hook_is_really_one_feature_worth_learning/

### 2. AI 中转站的便宜账开始算不平：慢、缓存失效、任务直接崩
- **来源**：V2EX
- **一句话人话版**：做 AI 中转的用户复盘发现，便宜之外还有 TTFT、缓存、错误处理和稳定性成本。
- **新闻/帖子本身**：楼主讨论自己做 AI 中转后的真实问题：速度变慢、首 token 时间变长、换号导致缓存命中下降，甚至 Codex 会把中转错误当成不可恢复错误。评论区没有停在“中转便宜不便宜”，而是开始算整体任务成本：如果链路不稳，agent 长任务中断、重试、上下文丢失，省下的单价可能很快被吞掉。
- **社区原话摘录**：
  - V2EX 1 楼：“找几个朋友合用 Pro 自建中转是最好选择。” —— 典型的折中派：不是完全不用中转，而是尽量自己控制链路质量。
  - V2EX 2 楼：“中转的价格占优势吗？OpenAI/Anthropic 的官方订阅，也相当于比 API 便宜几十倍吧？” —— 这条直接把讨论拉回总成本，不再只看 API 表面单价。
  - V2EX 6 楼：“我也不推荐用中转站，能用官方就用官方。” —— 稳定性压过价格，尤其适合长任务和 coding agent 场景。
- **参谋部短评**：这条很现实。agent 场景里最贵的不是单次调用，而是长链路失败后的恢复成本；中转站如果不能保证稳定，低价优势会被迅速抵消。

## 今日舆情温度

- **最热争议**：今天最明显的争议不是某个单一模型强弱，而是 agent 工具链进入生产使用后的“可控性”。Claude Code Hook、Opus 5 上下文污染、Codex 安全拒绝、DeepSeek 内测身份门槛都指向同一个问题：用户不再满足于模型能回答，而是要求流程稳定、边界清楚、失败可恢复。
- **最现实的吐槽**：最现实的是成本和稳定性。V2EX 的 AI 中转讨论很典型：单价便宜不等于任务便宜，TTFT、缓存失效、错误被 agent 误判为不可恢复，都会把一次长任务拖垮。Reddit 上 Hook 的讨论也是同一逻辑：能用确定性脚本做的事，就别反复烧 token 让模型重建。
- **最值得继续观察**：继续看两个方向：一是 coding agent 的流程基础设施，包括 Hook、orchestrator、跨会话通信、任务文件和 ADR 化记录；二是模型供应侧的信任边界，包括内测身份要求、安全拒绝一致性、模型版本口碑波动。真正影响采用的，往往不是发布会能力，而是这些日常摩擦。
