## 5. mcp-meta：把 104 个 MCP 工具折叠成 2 个，每轮 Schema 体积降 99.4%

作者实测：挂 14 个 MCP Server（104 个工具）时，不管用不用得上，所有工具的完整 JSON Schema 每轮请求都会强制塞进上下文，"模型还没读 Prompt 就先烧掉 14.2 万字符"。他的解法是在客户端和上游 Server 之间插入一层代理，只对模型暴露两个懒加载元工具——`mcp_tools`（看概览 / 按紧凑签名按需拉取某个 Server 的工具列表）和 `mcp_call`（指定 Server + 工具名调用）。接入后每轮 Schema 从 14.2 万降到 892 字符。纯标准库零依赖，前端 stdio、后端 stdio+HTTP（兼容 SSE、会话保持、分页、协议降级），MIT。本帖暂无回复。

值得关注：MCP 上下文膨胀已经是公认痛点，但主流做法是"少挂几个 Server"或逐个裁减工具；懒加载元工具这个思路是结构性的，而且对客户端零改造，值得拿来对照自己那堆 `mcp.json`。

https://www.v2ex.com/t/1254539

## 6. 开源了一个 agent 技能：把手机斜拍的文档重建成矢量 PDF，并附对照实验

这是一个给 Claude Code / Codex 用的技能，能把扫描件或手机斜拍照片重建为干净 PDF：文字可搜索可复制、图表流程图是矢量、放大不糊、版式贴近原稿——作者明确说，它不是"在图片上盖一层 OCR 文字"。更值钱的是评测：测试页由程序生成、每页有标准答案（练习册、表格、图表、流程图、表单、双栏文章，一半是带阴影的斜拍），按文字/版式/图形/矢量比例打分，每个模型跑两次（用/不用技能）。

- Fable 5.1：0.837 → 0.997；Sonnet 5.5：0.994 → 0.998；耗时上 Sonnet 九页从 25.7 分钟降到 16.2 分钟，Opus 和 Fable 反而变慢。
- 作者自己总结起作用的是什么：不是更长的提示词，而是**把 agent 容易错的步骤交给脚本**——按像素测量位置、把没把握的词裁出来放大、每次重建与原稿叠图逐页比对还缺什么。
- 局限也写得很干脆：测试集是合成的英文印刷页，手写和中文都没测；内置字体只有西文，起草脚本处理不了中文；如果只需要可搜索的文字，直接用 OCRmyPDF 更省事。

值得关注：这是"技能工程"的一个清晰样本——模型负责判断，脚本负责测量。失败版本也写进了 README（有一版让 Sonnet 退步，原因是照片比例算错）。
