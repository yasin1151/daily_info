### 1. 印度 CA 的八张中间证书私钥可以被反推出来，整个 HTTPS 信任链都受到了影响
- **来源**：HackerNews（564 分 / 294 条评论）
- **一句话人话版**：一家印度 CA 当年生成密钥的方式本身有缺陷，任何人拿公开证书就能反推出私钥，八张中间证书全部作废。
- **新闻/帖子本身**：出问题的是印度 CA 机构 eMudhra 的 8 张中间 CA 证书。不是“被偷”，而是密钥当年生成的方式有缺陷，从 2025 年 4 月起的时间窗内，任何人都能拿公开证书反推出私钥。报告人 10 月 17 日直接用这 8 个私钥各签了一条消息作为证据提交给各大根证书项目。Firefox 和 Chrome 当天拉黑，苹果 19 日跟进，证书已吊销。麻烦在浏览器之外：大量 IoT 设备、命令行工具、嵌入式客户端根本不消费吊销列表，必须升级软件才安全。好消息是证书透明度日志里没有这批中间证书的记录，说明期间没有发生针对浏览器用户的中间人攻击。评论区没有停留在事故本身，而是在问“为什么 2026 年还在用这套东西”。
- **社区原话摘录**：
  - HN 评论者（高赞）：“还要再读多少遍这种新闻，我们才肯把 Web PKI 换掉？我们明明已经有一套分层委托、出问题只影响子树的域名所有权系统，早点用起来吧。”—— 直接指向结构性方案，认为每次事故后的补丁式修复已经在重复太多年。
  - HN 评论者（高赞）：“Web PKI 是有诅咒的。凭什么为了吊销一张证书，就得通过一条可能已被攻破的 TLS 连接去更新 Go、Electron、webpki-roots？凭什么每个包都要自己塞一份高敏感的信任根？”—— 把矛头对准信任根的分发模型：吊销机制本身依赖网络，这条链路本身就是攻击面。
  - Mozilla 工程师回复（高赞）：“Firefox 用户两小时内就自动得到保护，Chrome、苹果、微软也有类似机制。但对生态里剩下的部分，几乎没有人投资吊销机制，对他们来说这是个大问题。”—— 官方口径承认浏览器侧可控，同时也承认浏览器之外是空白区。
- **参谋部短评**：这是今年最接近“全球性”的一次证书事故，值得盯的不是某家 CA 的运维，而是非浏览器客户端的信任库更新链条——包括自己机器上的命令行工具。
- **链接**：https://emudhra.we-have-a-problem.com/

### 2. Claude Code 的周额度是不是被悄悄调低了：一份 11.16B 到 3.67B 的对照
- **来源**：Reddit r/ClaudeCode（楼主自述从周六开始异常）
- **一句话人话版**：有用户发现 5 小时窗口半天就烧完，于是翻出前三周的 token 记录做对照，结论是这周额度只有上周的一半。
- **新闻/帖子本身**：楼主说从周六起 5 小时窗口的消耗“明显不对”，半天就没了，这是他第一次公开抱怨。跟帖里出现了少见的量化对照：一位 20 倍档用户翻出自己前三周的周总 token 量分别是 11.16B、16.39B、9.16B，而本周三天就烧到周额度 85%，实际只记录了 3.67B，折算满额约 4.32B，不到上周的一半。反方立刻给出方法学反驳：额度按 API 成本而非 token 数计费，缓存命中率、模型档位、effort 都会改变单价。帖内也有人说自己“反而还剩 30%”，说明更像是按账号、按时段的差异，而非全体下调。对按周采购额度的团队，这条的实际问题是：要不要为峰值预留第二份订阅，以及能不能留下自己的用量口径去和厂商对话。
- **社区原话摘录**：
  - Reddit 评论者（56 赞）：“My last three completed weeks show 11.16B, 16.39B and 9.16B total tokens, including cache reads.” —— 他还自己写了个小工具，把已经下线的用量面板用命令行里仍能取到的数据恢复出来。这条的说服力不在结论，而在给出了可复核的口径和时间窗。
  - Reddit 评论者（0 赞）：“Tokens are not enough. The limits are based on API usage costs.” —— 他补充自己本周 46% 用量对应 1600 美元 API 成本，正好落在每周 3500 美元的常态节奏上。方法学反驳：token 总数不能直接当计费单位，必须按模型、effort 和缓存拆分，否则对照不成立。
  - Reddit 评论者（5 赞）：“Been like shit for like 2-3 weeks now. I used to only have a single 20x sub, now you need two to handle large code bases.” —— 把个人体感升级成成本结论：大代码库场景下单账号已经不够，这会直接影响团队采购。
- **参谋部短评**：争议点不在“到底降没降”，而在用户拿不出厂商认的计量口径。凡是按周买额度的团队，都该先把自己的消耗记录留成可对比的账。
- **链接**：https://www.reddit.com/r/ClaudeCode/comments/1x99xhm/

### 3. Codex 变慢成了集体体感，同一天还赶上“重置”
- **来源**：V2EX 程序员节点、OpenAI 节点、X
- **一句话人话版**：一批用户反映 Codex 改个 bug 要半小时起步，与此同时官方正在重置额度，两件事叠在一起把“是不是在磨洋工”的怀疑推上台面。
- **新闻/帖子本身**：V2EX 一位用户说 6.1 Sol 开 fast 模式后，一次对话不是长时间思考就是无限重连，改个 bug 半小时起步。回帖迅速变成共鸣现场，并给出一个反直觉解释：慢不是算力问题，是“磨洋工”——同样一个月，Plus 用户额度没用完，活也没出多少。同一天 OpenAI 节点出现两条截然不同的帖子：一条是额度重置公告，35 楼里一片“血亏”，因为对重度用户来说重置等于已用额度清零重算；另一条是持续报 `Selected model is at capacity` 的故障帖，有人建议退出所有登录设备静置 24 小时。X 上 Codex 负责人当天先发 “Day 15 / We're cooked”，几小时后又改口 “Nevermind, we're still cooking... and reset. Enjoy.”，前一条约 4635 赞、2744 条回复，说明配额情绪已经很浓。
- **社区原话摘录**：
  - V2EX 1 楼：“会磨洋工了，给人一种 token 耐用的错觉。”—— 本轮最扎心的一句，把“变慢”重新定义成一种消耗节奏的调节，而不是性能故障。
  - V2EX 3 楼：“可太是了 plus 一个月都没用完，活也没出多少。。。”—— 给出量化体感：额度还剩很多，产出却没跟上；同一楼还补了一句“就这个月，之前也慢，但不像现在一个任务按小时算”。
  - V2EX 6 楼：“开启 fast 模式，用量消耗的快的一批。”—— 提醒 fast 模式本身是用额度换时间，于是“开快反而更慢”的观感里混着两种成本。
  - V2EX 重置帖 3 楼：“上午刚手动重置用了 15%。”—— 说明重置对重度用户是负资产，这条和“变慢”一起构成了当天最集中的信任损耗。
- **参谋部短评**：单次故障好修，信任损耗难修。真正值得盯的是用户开始用“故意放慢”来解释产品行为——这个解释一旦普及，之后的每次卡顿都会被算进账。

### 4. Gemini 4 Argon 一手编程实测：跑分拳打 Opus，实际 bug 越修越多
- **来源**：V2EX 分享发现节点
- **一句话人话版**：有人拿同一个 30 万行项目、同样的复现步骤对比 Codex 和 Argon，差距不在代码质量，而在流程。
- **新闻/帖子本身**：楼主 Codex 额度用光，拿一个 7 模块、30 万行代码的项目做 bug 修复，给两个模型同样的复现步骤和 adb 权限，对比 Codex（Astra xhigh）和 Antigravity 里的 Argon high。差别在流程：Codex 会自己操作 app 复现、抓日志、改完按步骤回归，一个 bug 十几二十分钟，说修好了基本是真修好；Argon 直接开改，不复现也不编译验证，单个 bug 干四十多分钟，最后“bug 确实复现不出来了，但流程根本走不到原来 bug 的位置”，再改下去整条链路都崩。另外 20 美元套餐两小时见底。Google 官方博客是拿它和 Astra、Opus 对比跑分的，这份实测是社区里少见的反向证据。
- **社区原话摘录**：
  - V2EX 1 楼：“啊，你没看发布介绍文章，强的点不在于编程啊，官方自己都说了写代码不厉害的，文科生模型来着。”—— 直接点破预期错位：宣传口径和用户拿它干的事本来就不是一回事。
  - V2EX 2 楼：“google 自己的对比，这可是拳打 Astra 脚踢 Opus 啊。”—— 用官方跑分反讽；同一串 4 楼马上回“你不要看评分啊，你们都不看实际体验的吗”。这两条把当天“跑分 vs 体感”的对立摆得很清楚。
  - V2EX 6 楼：“还好吧。我用着 感觉还可以正常开发问题不大 当然我是个人项目。”—— 少数正面样本，也划出了边界：个人项目够用，大工程的多步回归不行。
- **参谋部短评**：这条的价值不在谁更强，而在它把“会不会验证”单独拎了出来。选模型时先问对方跑不跑回归，比看榜单准。

### 5. Cloudflare 把 TypeScript 编译器移植成 Rust，一句“我一行代码都没写”让人不安
- **来源**：HackerNews（331 分 / 147 条评论）
- **一句话人话版**：Cloudflare 联合 Vite 团队把 TypeScript 编译器重写成 Rust 版，官方基准快最多 8 倍，但文章里承认移植过程大量由 AI 完成。
- **新闻/帖子本身**：tsrs 由 Cloudflare 和 VoidZero（Vite 团队）联合 Owner.com 的工程师完成，放在 Oxc 工具链里孵化，并与 TypeScript 团队紧密合作——明确不 fork，语言设计权仍在微软手里。官方基准：同等 type check worker 数下比 TypeScript 7.0 快最多 8 倍、内存少约 70%；TS 7.1 beta 已吸收部分优化，比 7.0 快 2.5 倍。真正的动机不是“想更快”，而是 Cloudflare 要在纯 WASM 沙箱里跑完整类型检查：把 Go 版编译成 Wasm 得把 GC 一起打包，太重，Rust 与 Wasm 主机交互干净得多。评论区一半在讨论这个动机，一半在讨论“AI 主导的大规模移植”能不能被信任。
- **社区原话摘录**：
  - HN 评论者（高赞）：“很高兴看到速度提升，但文章里那句‘我一行代码都没写’让我不安。我们要从精心手写的移植，转向完全由 AI 生成的移植。我知道行业在往这走，我自己也大量用 agent，但我会 review 它们的输出，因为它们经常出问题。”—— 这条代表了相当一部分资深开发者的真实态度：不是反对用 agent，而是反对把 review 这一环省掉。
  - HN 评论者：“不是‘我们想做个更快的 Rust 编译器’，那是副作用。他们需要能在 WASM-only 沙箱里跑的 TS 编译器。”—— 把宣传口径和技术动机分开，提醒读者别把顺带的性能红利当成项目目的。
  - HN 评论者：“他们的需求和普通 Web 开发者的迭代周期完全不同，他们是要跑几百万次来省成本。你几乎肯定不需要马上计划迁移。”—— 降温派，反对把大厂的基础设施优化直接当成自己的路线图。
- **参谋部短评**：这可能是第一批公开承认由 AI 主导完成的大规模编译器移植，值得盯的不是 8 倍，而是它之后怎么被维护、出问题时谁来读那部分代码。
- **链接**：https://blog.cloudflare.com/typescript-rust-port/

## 今日舆情温度

- **最热争议**：额度和速度到底是不是被“调”了。Claude Code 那边有人拿出 11.16B 到 3.67B 的对照，Codex 这边有人用“磨洋工”解释卡顿，官方又在同一天重置额度。争论的实质是用户体感和厂商计量口径对不上：一方只有感受和 token 数，一方按 API 成本计费且不公开拆分。目前没有一方能说服另一方，但“该不该留自己的用量账”已经从极客习惯变成了团队采购问题。
- **最现实的吐槽**：订阅成本里藏着一块固定的“网络税”和“路由税”。有人为了 Claude 不封号在算 SD-WAN 几万、自建家宽 400 元每月、eSIM 一次买断三条路；有人买 10 美元套餐半小时就把周额度用到 20%，回帖一致指出问题在按高价模型路由——“GLM 本就不便宜，便宜的是 DS”。这类吐槽比任何模型评测都直接：钱是怎么在看不见的地方被烧掉的。
- **最值得继续观察**：一是闭源语音模型的反弹，某家把语音识别、合成和实时推理做成闭源 API 后，评论区直接变成“本地语音方案推荐会”，用户真正在意的是语音数据不出机器；二是 agent 的可靠性工程，从“跑到一半崩了怎么办”到“测试写成串行导致一个任务跑一小时”，同一天多个来源指向同一件事——决定 agent 能不能真用起来的，是故障后的行为和执行纪律，不是榜单。

## 可以跳过

- 一堆“给 agent 加技能”的新项目：求职、安全审计、SEO、写码习惯各有爆款，但页面基本只有 star 数和作者自述，缺少真实使用者的反馈，只能当趋势背景看。
- 与 AI 工作流关系不大的高热度小游戏：讨论很热，评论也有趣，但对判断工具链和成本没有信息量。
- 各家工具“已接入最新模型”的公告：属于常规更新，没有价格、额度或能力上的实质变化。
- 宏观预测和行业口号类内容：只有观点没有具体产品动作，读完无法改变任何决定。
