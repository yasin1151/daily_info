## X / Twitter

**Box CEO Aaron Levie（levie on X）**

他给了一个挺硬的试金石，用来判断自己 AI 用得够不够狠：如果你现在做的事，在没有 AI 的时候你也能做出来,那你大概率没用够。

原话大意是,大概半年前,AI 能做到最好的程度也就是帮你把本来就要产出的东西做快一点;但现在进入了一个新阶段,和 AI 一起工作的产出应该「大幅超过」你原本能做到的水平,而且只花零头时间。他落到每个环节上：产品原型不只是能跑能交互,功能本身就该比原来强;工程架构应该能拿到以前不敢想的性能收益;项目调研应该把这个题目所有维度的事实全吃干净;业务流程应该完全换一种跑法,并且能从自己过去每一次失败里学习。

他还补了一句判断：「AI 会在大多数维度上比我们更聪明,但智能仍然是锯齿状的」——关键是叠加人类擅长的部分,拿质变的结果,而不是线性提速。

为什么值得看：这是目前对「AI 到底该怎么用」最可操作的判据之一,不依赖任何具体工具,可以直接拿去问团队。

## 播客

**Latent Space — Using Agents for Long-Horizon Financial Work — Aman Singh, Arca**
https://www.youtube.com/@LatentSpacePod

一句话结论：真正难的从来不是让 agent 会干活,是让它在跨度十天的任务里始终知道「世界现在是什么状态」,并且敢把记忆和 harness 攥在自己手里不放。

**背景**：Arca 是一家 AI 原生财富管理公司,最近融了 6400 万美元。Aman Singh 带 AI 平台团队,负责底层 harness 和「用 AI 跑整个业务」的能力。他强调一句定位——「我们不是 SaaS 公司,我们就是这家公司本身」。这句话不是修辞,后面几乎所有的技术选择都从它推出来。

**模型选择：不看外部榜单,只看自己的 benchmark。** 他们换过好几代模型（Gemini → OpenAI → Anthropic,现在 Claude 为主）。最近有个新模型 Luna,外部 benchmark 吹得很好,但他们内部测下来「比预期差不少,太慢,而且很贵」,于是没用。这条对自研引擎的人应该是熟悉的信号：外部跑分和你业务 harness 上要表达的能力,基本是两件事。他们按任务复杂度分层,税务分析走最重的 tier,后台活动走轻量 tier,advisor 完全感知不到这个路由。

**长时任务的真正解法是状态,不是上下文窗口。** 一个报税场景会横跨十天。中间会不断有信号进来：邮件线程里的回复会回到同一个 agent,但一个突然打进来的电话是全新信号,由一个「刚醒来」的 agent 接手。它靠内部记忆系统搞清楚眼前发生了什么事——对每个客户持久记录:现在在做什么、谁负责什么、已经发生了什么、接下来几天必须发生什么、长期在盯什么。另外还有一个他称为「dreaming」的例行动作,每天反思这个客户的状态并回写记忆。所以新 agent 能立刻知道「哦,我们正在执行一笔大的税务操作,我手上这个信号和它有关」。

**安全是确定性的,而且只收在能力边界上。** 这是整期最值得抄的部分：
- 分析全自动,但任何资金移动、资产清算、直接对客沟通,一律人类在环。他们有和托管方的深度 API 集成,能做,但主动不做。
- 每一次写数据库的工具调用,都跑一个快的 LLM 做校验。
- 提示注入防护做在边界上——邮件、文档、电话进来时先检测。
- 数据出境（web 搜索、发日历邀请这种)双重把关：确定性检查已知 PII,再加一组小模型投票看是不是在尝试外泄。
- 他的原则原话是「把约束收在能力边缘,不要提前」——不要因为怕,把 agent 的能力提前阉割掉。

**沙箱的用法和大多数人反着来。** agent 本身不在沙箱里,沙箱只是它卸载计算的工具。agent 用代码查数据、聚合、算,产出财务计划 PDF;关键一步是把代码翻译成一种严格的中间格式,然后「把代码扔掉」,只对格式加校验再进后端。产物出来之后才跑验证：确定性检查有没有裸账号,小模型检查有没有「承诺收益」这种合规红线。他还讲了一句挺有意思的：这件事比人类做得好,因为 AI 在发现最细微的不合规措辞上不知疲倦。

**一个很具体的坑：模型对陈旧金融知识的自信。** 他说模型会很自然地拿 2025 年的税率档去算 2026 年的账,而且算得理直气壮。所以他们在 harness 里挂了 decision model,一旦模型要给出金融建议,就把它顶到已验证的知识库或者触发搜索。这是「拥有 harness」的直接好处——你能在真正要紧的地方补准确率。

**为什么拒绝 managed agents（对自研引擎最相关的一段）：** 他明确说对 Anthropic、OpenAI 的模型非常看好,但对「managed agents 这类产品」持保留。原因不是质量,是所有权：managed agents 的核心恰恰是模型如何持久化、如何贡献记忆、以及那些让它成功的运营知识。「把这部分交给别人,是一种风险。拥有你的智能,才意味着你有能力去影响这门生意。」如果交出去,你就失去了做真正贴合业务、深到能改变业务的那种东西的控制权。

**反馈闭环,以及为什么不能让 agent 自己改 prompt。** 每一次员工编辑或取消,都必须写「为什么」,这个 why 和对应的 agent trace 一起入库,成为 eval。每天晚上他们拿真实世界跑出来的 trace,在上面跑一个 meta agent,让它提 harness 改动的建议——哪个工具在误导、哪里报错、知识库缺什么。但上线前一定有人类工程师在环,原因他说得很直白：agent 改 prompt 会改得很脏,「每一个小修复最后会变成整个 prompt」,它们没法保持 meta,没法把修复泛化。

**一个客户案例**：一位潜在客户已经有 advisor、年费 1500 美元,但对方不太回消息。他们的 agent 读完所有材料后发现了两件事——有一笔客户不知道的费用,以及这位 advisor 根本不是 fiduciary（没有受托义务)。这类「人类在规模上很难持续盯住」的细节,恰好是 agent 的默认行为。

为什么值得看：这期是目前少见的、把长时任务、记忆、确定性护栏、沙箱边界、eval 闭环这几个东西在同一套真实业务里讲透的材料。尤其「拒绝 managed agents、把智能攥在自己手里」和「约束收在能力边缘」这两条,基本可以直接作为自研引擎的架构原则来用。
